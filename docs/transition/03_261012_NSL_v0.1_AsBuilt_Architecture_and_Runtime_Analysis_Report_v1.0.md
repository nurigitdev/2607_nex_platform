
# NSL v0.1 As-Built Architecture and Runtime Analysis Report v1.0

**Phase:** P3 — NSL v0.1 As-Built Analysis  
**Baseline:** `nurigitdev/2608_nsl` tag `v0.1`  
**Commit:** `803f22aadc3946a48b05472c80b60fe11d9d9554`  
**Important:** This report reconstructs NSL v0.1 independently. It does not yet compare it with NSL v0.2.

---

## 1. Executive Summary

NSL v0.1 is already a substantial deterministic execution product, not a language prototype.

Its implemented architecture includes:

```text
Source / Include Composition
→ Lexer / Parser / AST
→ Static Types / Symbols / Bounds
→ Compiler
→ Immutable SkillObject
→ Canonical .nso
→ Deterministic Runtime
→ Canonical READ Tool Gateway
→ CHECK / EMIT
→ Structured ExecutionResult
→ Audit / Protected Snapshot
→ Replay
→ Deterministic .nsp Package
→ Signature / Package Verification
→ Framework-neutral NeX-AE Worker Integration Contract
```

v0.1 is deliberately **READ / READ_VALIDATE only**.

The following are explicitly outside v0.1 scope:

```text
WRITE
APPROVAL
Workflow Language
Multi-Skill Orchestration
Scheduled execution as NSL syntax/IR
```

Schedule is defined as a Platform extension that repeatedly submits one registered Skill through the same execution path.

## 2. Product Definition

Repository README definition:

> NSL is a deterministic execution kernel that executes a NeX-AE-selected business Skill under constrained rules and canonical Tool contracts.

The production boundary is intentionally narrow:

```text
LLM / Agent
→ selects / prepares Skill inputs

NSL
→ deterministic execution only

Business systems
→ accessed only through ToolExecutionPort
```

NSL Runtime has no direct dependency on:

- filesystem
- network
- SQL
- web framework
- NeX-AE
- LLM

## 4. Risk / Capability Boundary

Compiler accepts only:

```text
READ_ONLY
READ_VALIDATE
```

Required Tool contracts must resolve exactly and:

```text
ToolContract.capability == READ
```

A WRITE-capable Tool is rejected at compile time.

Negative acceptance explicitly contains:

```text
AC-N03
WRITE Tool compile reject
```

Therefore:

> WRITE absence in v0.1 is an intentional scope boundary, not an implementation defect.

## 6. Data Semantics

### Presence

```text
PRESENT

```

### Completeness

```text
COMPLETE

```

### Check status

```text
PASS
FAIL

```

### Data classification

```text
PUBLIC
INTERNAL
CONFIDENTIAL
RESTRICTED
```

Core safety rule:

```text
COMPLETE + TRUE
→ CHECK PASS

PARTIAL / UNKNOWN
→ never false PASS
```

Tool Failure is explicitly different from Empty/Presence.

## 7. Static Safety / Resource Bounds

Compiler and Runtime enforce bounded execution.

Skill limits include:

```text
tool_calls
loop_iterations
emitted_rows
collection_size
duration
```

The compiler statically proves or rejects:

- Tool-call upper bounds
- Loop/collection bounds
- Emit-record bounds
- Unsupported unbounded execution

Runtime rechecks actual resource use.

The certification suite explicitly validates:

```text
999   → success
1000  → success
1001  → LIMIT_EXCEEDED before unsafe continuation
```

## 9. Runtime Entry Model

`ExecutionRequest` requires:

```text
execution_id
inputs
runtime_context
principal
data_policy
```

The execution ID:

- must be caller supplied
- is not generated by Runtime from time/random/UUID
- is preserved in success/failure result
- is not part of expression semantics

Thus:

```text
ExecutionId
= execution identity

not
= semantic input
```

---

## 10. ExecutionContext

Each execution creates a fresh isolated context.

Namespaces are physically separated:

```text
input_values
context_values
variable frames
check frames
checks log
outputs buffer
invocation counter
resource meter
```

Bindings are write-once.

FOREACH pushes/pops variable/check frames and cleans them through `finally`.

No ambient mutable state is used for Skill semantics.

---

## 11. Determinism Contract

For identical:

```text
Skill
Execution inputs
Runtime Context
Tool Results
```

the Runtime guarantees deterministic semantic output.

The repository tests repeated execution for:

- immutable ExecutionResult
- ordered Statement/Tool/CHECK/EMIT audit events
- deterministic invocation IDs beginning at `inv0001`
- output/check order
- resource usage

Time/random/UUID are not exposed as implicit Skill semantic inputs.

Required time must enter through declared Runtime Context.

## 13. Principal and Authorization

Production-form execution requires an `ExecutionPrincipal`.

Fields include:

```text
TenantId
SubjectId
ActorType = USER | SERVICE
Roles
Scopes
AuthContextRef
Verification
OnBehalfOf (optional)
```

Credential material is forbidden in the Principal.

Production integration requires:

```text
PrincipalVerification = VERIFIED
```

Runtime does not authenticate credentials itself.

It requires an already validated Principal and authorization context.

---

## 14. Authorization Granularity

Authorization is evaluated at two levels:

```text
Skill execution authorization
+
each Tool-call authorization
```

Required scopes must be explicit.

Tool Binding and authorization are tenant/principal/scope-aware.

Audit records:

```text
AuthorizationDecisionRef
```

rather than raw credential material.

## 15. Data Handling Policy

Execution carries an explicit policy containing:

```text
max_trace_classification
snapshot_retention_days
audit_retention_days
```

Runtime projects only declared inputs/context.

If undeclared runtime data is observed, audit classification fails safe toward `RESTRICTED`.

## 16. READ Execution Boundary

Canonical READ path:

```text
ReadExpr
→ required tool_ref
→ exact ToolRegistry.resolve
→ Skill required scope check
→ Tool authorization
→ ToolCallRequest
→ ToolContract request validation
→ timeout-bounded ToolExecutionPort

→ audit/provenance
→ ValueEnvelope
```

Runtime depends on the abstract `ToolExecutionPort`, not Mock/MCP concrete implementations.

---

## 17. CHECK / False-PASS Prevention

CHECK is strict.

Important semantics:

```text
COMPLETE + expression TRUE
→ PASS

COMPLETE + expression FALSE
→ FAIL

PARTIAL or UNKNOWN
→ UNKNOWN
```

A Tool error cannot be converted to an empty successful value.

This is a core v0.1 safety feature.

---

## 18. EMIT / Structured Result

EMIT:

- must exactly match declared output schema
- carries field-level classification
- is bounded by `emitted_rows`
- is ordered deterministically
- is returned as structured immutable records, not free-form text

---

## 19. Audit

Runtime creates structured audit events for:

- execution start/end
- statement processing
- Tool call lifecycle
- CHECK results
- EMIT
- errors/resource outcomes

Sensitive values are not blindly stored in normal audit events.

Instead audit references protected snapshots and hashes.

Audit storage can maintain retention metadata separately from semantic deterministic event content.

---

## 20. Snapshot Security

High classifications:

```text
CONFIDENTIAL
RESTRICTED
```

must be sealed by protected snapshot storage.

Snapshot references bind:

```text
Tenant
Classification
Value hash
Retention
Expiry
```

Read access requires:

```text
verified Principal
scope nsl:replay:read
same tenant
valid reference metadata
not expired
```

Delete requires:

```text
nsl:snapshot:delete
```

Cross-tenant snapshot access is forbidden.

---

## 21. Replay

Replay does **not** call the original external Tool provider.

Flow:

```text
Original Execution
→ protected Input/Context/ToolResult snapshots
→ ReplayBundle
→ ReplayToolExecutor
→ same RuntimeEngine
→ deterministic result comparison
```

Replay verifies:

- Skill semantic hash
- Tenant
- Tool call order
- Tool identity/version
- Argument hash
- complete consumption of recorded calls

Result comparison produces deterministic JSON-pointer differences.

## 22. NSP Package

NSL v0.1 implements deterministic deployment packaging.

```text
canonical NSO(s)
→ NspBuilder
→ canonical Manifest
→ deterministic ZIP_STORED .nsp
```

Container characteristics:

- fixed timestamp
- fixed file mode
- deterministic member order
- canonical `manifest.json`
- canonical NSO member names
- no caller-controlled archive path
- package content SHA-256

---

## 23. NSP Trust / Signature

Untrusted package path:

```text
untrusted NSP bytes
→ NspVerifier
→ archive/path/resource checks
→ canonical manifest check
→ NSO hash/identity/semantic check
→ package hash
→ environment signature policy
→ Ed25519 verifier
→ VerifiedNspPackage
```

Production policy requires verified signature.

Trusted keys are:

```text
key_id → Ed25519 public key
```

Unknown key, wrong key, modified signature, package tamper and downgrade are rejected fail-closed.

Runtime/Compiler core do not implement cryptography directly; cryptographic adapter lives under `nsl.adapters.ed25519`.

```text
VerifiedNspPackage
```

```text
exact SkillId
```

## 26. Skill Execution Worker

Framework-neutral worker:

```text
SkillExecutionWorker
```

Required dependencies:

```text
RuntimeEngine
SkillResolver
ToolExecutionPort
AuditSink
optional SnapshotStore
ProgressSink
```

Certified production evidence profile:

```text
WorkerEvidencePolicy.SNAPSHOT_REQUIRED
```

requires a SnapshotStore.

Execution sequence:

```text
validated SkillExecutionJob
→ progress STARTED
→ Verified Skill resolve
→ semantic identity check
→ progress SKILL_RESOLVED
→ progress RUNNING
→ RuntimeEngine.execute
→ terminal progress COMPLETED or FAILED
→ RuntimeResultEnvelope
```

Runtime failure is not promoted to successful completion.

---

## 27. Progress Contract

Progress states:

```text
STARTED
SKILL_RESOLVED
RUNNING
COMPLETED
FAILED
```

Progress is ordered per ExecutionId.

Progress events intentionally exclude:

- raw Input
- Runtime Context values
- Tool arguments/results
- credential material

## 28. Result / LLM Explanation Separation

NSL v0.1 implements separate record types:

```text
RuntimeResultRecord
LlmExplanationRecord
```

The explanation is hash-bound to:

```text
RuntimeResultHash
```

and cannot redefine Runtime status.

Stores are separate interfaces:

```text
RuntimeResultStore
LlmExplanationStore
```

This is a deliberate architecture boundary: deterministic runtime truth and LLM explanation are separate.

Actual NeX-AE persistence integration remains an external end-to-end verification item.

---

## 29. Dispatch Boundary

NSL includes a framework-neutral dispatcher port.

Development fake:

```text
InMemoryJobDispatcher
```

Dispatch identity currently uses:

```text
ExecutionId
```

Duplicate ExecutionId submission is forbidden.

The NSL repo itself does not implement the actual NeX-AE API thread, durable Queue, or worker host.
