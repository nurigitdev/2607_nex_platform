
# NeX Platform v1.0 As-Built → v2.1 Frozen Mapping & Delta Consolidation v1.0

**Process Step:** Step F — v2.1 Frozen Mapping and Delta Consolidation  
**Inputs:** P1 Platform v1.0 As-Built + P2 Early Agent As-Built + P3 NSL v0.1→v0.2 Delta + Integrated Frozen v2.1 Baseline  
**Purpose:** Fix the transition boundary before any P4 code change.

---

## 1. Executive Conclusion

The v1.0 implementation is a strong foundation for v2.1, but the transition must be an **identity-preserving architectural extension**, not a rename/refactor sweep.

The safest strategy is:

```text
Keep v1.0 service boundaries and working RAG behavior
                │
                ▼
Add canonical Agent Runtime identities around existing behavior
                │
                ▼
Integrate NSL v0.2 READ through the new runtime
                │
                ▼
Add WC / Multi-Agent work
                │
                ▼
Add Controlled WRITE / Approval / Enterprise OS
                │
                ▼
Add WA / Schedule / final conformance
```

The highest-risk mistake would be to reinterpret existing identities as target identities.

---

## 2. Identity Migration Rule

The following must remain distinct:

```text
v1.0 InteractionId
!= v2.1 AgentExecutionId

v1.0 CX JobId
!= v2.1 AE RuntimeJobId

v1.0 CX GenerationId
!= NSLExecutionId

v1.0 GeneratedResponseId
!= AgentResultId

request_id
!= BusinessOperationId
```

Migration rule:

> Preserve the old object and add the new canonical identity as an explicit reference.

This permits rollback, regression comparison and incremental rollout.

## 6. RuntimeJob Decision

The existing common JobQueue is reusable infrastructure, but existing CX generation jobs are not the target AE RuntimeJob.

Target model:

```text
AgentExecution 1:N AE RuntimeJob
```

with types:

```text
START_EXECUTION
CONTINUE_EXECUTION
RESUME_EXECUTION
RETRY_EXECUTION
RECONCILE_EXECUTION
PUBLISH_RESULT
RECONCILE_PUBLICATION
```

A RuntimeJob may itself invoke the legacy Chat/RAG logic, which can enqueue a separate CX generation Job.

Therefore:

```text
AE RuntimeJob
→ may cause/use CX Job

but

AE RuntimeJob != CX Job
```

---

## 7. ChatInteraction Decision

The v1.0 ChatInteraction remains useful as:

- UI request/interaction record
- backward-compatible API state
- interaction idempotency boundary
- workspace conversation history

It should **not** become the AgentExecution table by renaming.

Recommended migration:

```text
ae_chat_interactions
  + agent_execution_id nullable/reference during migration
```

P4 can initially maintain:

```text
PROMPT Interaction
→ exactly one wrapper AgentExecution
```

without removing existing Interaction semantics.

User-initiated "retry" and technical RuntimeJob retry must later be distinguished explicitly.

---

## 8. Result Decision

v1.0:

```text
Chat terminal state
+ GeneratedResponse
+ Artifact
```

Target:

```text
AgentResult
+ ResultDelivery
```

Migration:

```text
GeneratedResponse stays the private/generated content identity.

AgentResult
→ references or summarizes GeneratedResponse
→ contains structured_result/business/evidence/artifact refs
→ is the logical Agent completion result.
```

Do not rename GeneratedResponse to AgentResult.

## 9. CX / MO Responsibility Migration

The v1.0 RAG pipeline is valuable and should remain working.

For the transition:

```text
Existing RAG flow
AE → CX retrieval → CX grounded generation → MO
```

can be wrapped as a known compatibility ExecutableStep.

Over time, Frozen target responsibilities should become clearer:

```text
CX = Context / Evidence
MO = Model Serving / Routing
AE Runtime = orchestration / plan / result
```

The first P4 slice should not refactor this mature provider path prematurely.

```text

NSL
WRITE
Approval
Schedule

```

This scope prevents phase leakage.

## 14. P4 Migration Safety Rules

1. `v1.0` tag remains immutable.
2. Work occurs on a dedicated transition branch.
3. Existing public Chat API contracts remain backward compatible.
4. Existing v1.0 tests must pass.
5. New runtime identities are additive.
6. No existing CX Job is reinterpreted as AE RuntimeJob.
7. No Chat Interaction is reinterpreted as AgentExecution.
8. No GeneratedResponse is reinterpreted as AgentResult.
9. Database migration is additive and rollback-safe.
10. Feature flag / compatibility path should allow old behavior if the runtime wrapper is disabled.
11. P4 uses IA/PROMPT only.
12. Any WC/NSL/EOS finding goes to Issue Register, not into P4 code.
